# 回答入力画面

[索引](../design-index.md) / [DB](../data-model.md) / [画像](../images.md)

## 目的・データ取得

`/entry`、user/adminともログイン必須。get_event_settingsで受付対象の開催回・期間・ルール・2名のキャラクター・応募部門設定を取得し、そのevent_idと本人user_idでsubmissionsをmaybeSingle取得します。タイトルは開催回名、ページ画像はentryImageです。この画面に過去回を選択するUIはなく、共通Headerから[参加履歴](history.md)を開いて過去の参加情報・得点・提出画像を確認します。

共通Headerにライト／ダークテーマの切替を表示します。端末連動と保存規則は[共通設計](../architecture.md)を参照します。

## 1つ上の順位のポイント

受付中だけ、通知群の下・入力フォームの直前に「1つ上の順位のポイント」を表示します。PC・スマートフォンとも同じ順序です。`get_my_rank_neighbor(p_event_id)`で、現在開催回の本人の**保存済み回答**と同じキャラクター・応募部門から、確認済み得点の降順、同点は回答更新日時の昇順で直前の相手の得点を取得します。上位10名に限定しません。相手の名前・画像・自分の順位・点差は表示しません。

- 相手がいる場合は得点をja-JPの桁区切りで表示。0点も表示します。
- 本人が1位なら「現在1位です」。
- 未回答・未確認・無効・得点未登録で本人に順位がない場合は、見出しを含め欄全体を非表示。
- 取得中はスピナー、失敗時は「ポイントを取得できませんでした」。フォーム入力は維持し、再試行ボタンは設けません。

画面表示時と保存成功後に取得します。未保存のキャラクター選択には追従せず、画面を開き直すと再取得します。本人ID・開催回ID・保存後の更新番号をコンポーネントのkeyにし、変更時に読込状態へ戻します。離脱後の古い応答は反映しません。受付期間の境界で既存の設定再取得が行われると表示可否も更新し、期間外はエラーやスピナーも含め非表示です。RPC側も受付中のactive開催回だけを許可します。

画面・保存後更新・遅延応答をコンポーネントテスト、順位計算・権限・期間境界をローカルDBテストで確認しています。ブラウザー未接続のためPC／スマートフォンの実描画・手動操作は検証保留。[検証記録](../verification.md)を参照してください。

## 入力項目

| 項目 | 入力制約 |
| --- | --- |
| サーバー内ユーザーネーム | trim後1〜100文字、必須 |
| ゲーム内プロデューサーネーム | trim後1〜100文字、必須 |
| 育成キャラクター | 開催回設定から選択。enabledまたは既存回答のIDに一致する候補を表示 |
| 応募部門 | 開催回の1〜10部門をorder順に表示し設定名称・補足を使用。必須。新規回答で1部門なら自動チェック、複数部門なら選択。既存回答があればdisabled |
| 評価値・最終所持スキルカード画像 | 任意、1ファイル |
| PID・Pレベル画像 | 選択部門のrequiresProof=true時に必須（既存画像で代替可） |
| 総出席日数画像 | 選択部門のrequiresProof=true時に必須（既存画像で代替可） |

選択した部門の参加条件文を改行を保持して表示し、空欄なら表示しません。既存回の初期値は現在の初心者条件等を維持しますが、案内文は管理者が編集できます。数値入力・OCR・ゲームAPIで資格を判定する実装はありません。画像の形式・サイズ・変換は共通画像設計を参照。

## モーダルと状態

- 初回読込中はスピナー。読込完了後、当該回の回答がなければルールモーダルを画面マウントにつき一度自動表示。回答済みは自動表示しない。ボタンから再表示可能。
- ルールは改行を保持し、空の場合は未登録メッセージ。
- 非受付期間は入力fieldsetと送信をdisabled。開始前／終了後をサーバー時刻と設定で区別して通知。
- 期間境界+約1秒で設定を再取得するタイマーを設定。遅延はブラウザー上限2,147,483,647ms以内。
- 送信要求で項目検証し、問題がなければ「送信内容の確認」。新規と上書きで本文を変える。
- 確定後に最新設定を再取得し、受付中なら保存。送信ボタンはsubmittingで無効化。成功は通知、回答再取得、画面上部へスクロール。

## 保存とエラー

entryServiceは既存回答の応募部門を優先し、event_id/user_idをキーにupsertします。新しい画像がなければ現行形式の既存パスを保持。新規・差し替えは画像アップロード→DB参照変更→旧画像削除の順です。新規保存のdeckはnull。旧deckがある回答は結果画像未提出扱いとなり、再保存時に旧score/deckの解消を試みます。

圧縮・アップロード・保存・期間外を固定日本語文言で表示し、失敗時に入力値を維持します。upload/database失敗時は期間を再確認し、受付終了なら期間外メッセージへ変換します。既存画像の取得失敗は画像欄に表示します。

画像選択UIはレビュー状態を取得せず、確認済み/無効でも選択できます。実保存ではDBが画像パス変更を拒否します。キャラクター/結果画像の実差分はレビューを未確認へ戻します。名前変更・初心者証明だけでは戻しません。

## 現行の制限

イベント設定の取得失敗・active回なしではfailureを設定しますが、回答取得が開始されずloadingが残る経路があります。エラー文言を必ず閲覧できるとは限りません。

開催回変更や回答未存在時に既存フォームを明示的に初期化する分岐はありません。送信時の最新event_idと、すでに読み込んだexisting/valuesを併用するため、開いたままの開催回切替を完全に同期する設計ではありません。

## 照合シナリオ（ソース確認）

- 新規／既存／期間外で入力可否・ボタン文言・確認本文が変わる。
- beginnerだけ2画像必須、結果画像は任意。
- 部門固定はUI・保存処理・DBで適用。
- 画像保存失敗時の新画像回収と、成功後の旧画像削除を区別。
- レビュー後の画像制限とレビューリセットは別のDB処理。

## 部門と証明の保存境界（2026-11-24）

部門の固定列挙を廃止し、開催回設定から名称・補足・選択部門の条件文・証明欄を表示。validateEntryで所属部門と証明2点を検証します。送信確定時にも最新設定を取得し、saveEntryは未知部門・必須証明不足を画像アップロード前に拒否。編集中に削除された部門への回答はDBも拒否します。既存回答の部門ID変更禁止とレビュー済み画像の保護は維持。[DB](../data-model.md)。


## 単一部門の自動選択（2026-11-24、v13承認後）

開催回設定と本人回答の読み込みが完了し、保存済み回答がなく応募部門が1件だけの場合、唯一の部門IDをvalues.entryDivisionへ設定し、カードを自動チェックします。送信値も同じIDです。複数部門では新規未選択を維持し、保存済み回答は既存の部門を優先。名前・キャラクター・画像など他の入力を保持し、自動保存や自動送信は行いません。

再訪・再ログイン・設定再取得でも同じ規則を適用。選択部門の参加条件文と証明画像欄・必須検証は従来の処理へ連動します。本人回答の取得中は自動選択せず、保存済み回答を上書きしません。DB/API変更なし。
