# 学マスイベントアプリ開発

`$gakumasu-dev 回答一覧に応募部門の絞り込みを追加したい` のように、コマンドと短い要望で開始する。日本語で対話し文書を作る。このスキル自体の作成・編集依頼では、アプリの開発フローを開始しない。

## 正本設計書の入口

- 最初に [docs/design-index.md](../../../docs/design-index.md) を読み、[共通設計](../../../docs/architecture.md) と索引で対応付けた `docs/screens/` の対象画面を参照する。
- DB・権限変更は [data-model.md](../../../docs/data-model.md) と [api.md](../../../docs/api.md)、画像変更は [images.md](../../../docs/images.md)、起動・CI変更は [operations.md](../../../docs/operations.md) も読む。
- 更新先はこの既存構成へ統合する。画面追加・削除は索引も更新し、設計書の相互リンクと実装根拠を維持する。[照合記録](../../../docs/verification.md) は確認時点と方法の記録であり、将来の変更の検証済み証拠として流用しない。
- 現状の文書化・設計書の整備だけを依頼された場合は、実装を正本として必要な調査と文書更新を行う。新機能開発向けの一時仕様書・設計・コーディング・手動テストの全フローは開始せず、指定された照合回数と確認方法を記録する。

## 1. 対象確認と一時仕様書

- 対象は `gakumasu-server-event-app`。現在のワークスペースから探し、この環境での既定候補は `C:/Users/zgmf_/Desktop/gakumasu-server-event-app`。`package.json` のnameとソースで確認し、別アプリを変更しない。見つからない場合だけ場所を質問する。
- 適用されるAGENTS.md、作業差分、README.md、既存docs、該当実装を読む。利用者の未コミット変更を保持する。PowerShellの日本語ファイル読み書きはUTF-8を明示する。
- **実装に先立つ最初の成果物として、一時仕様書の草案を作成する。** OSの一時ディレクトリに `gakumasu-dev/<日時と一意なID>/` を作り、`spec.md` に要望・対象範囲・既知の要件・未決事項を記入する。同じ場所に後述の `design.md`、`verification.md`、証跡を保存する。パスを開発者へ伝える。作業の中断・再開に備え、現在の段階と次の作業も記録する。
- 既存仕様の調査結果と今回の要望を区別する。READMEやPROMPT.md、PROMPT2.mdと実装に食い違いがある場合、今回の受入条件に影響する点を未決事項にする。

## 2. 決定事項を数えて対話する

- コードや既存仕様から確定できない、利用者に見える振る舞い・対象者・権限・入力条件・データの扱いなどを列挙する。内部実装の選択で解決できることまで開発者に決めさせない。
- **最初の質問を出す前に**「仕様確定に必要な決定事項は N 件です」と件数および番号付きの議題一覧を提示する。質問のメッセージ数ではなく、独立した決定の数を数える。0件なら0件と伝えて先へ進む。
- 利用可能なら対話型入力ツールで1〜3件ずつ質問する。必須の仕様回答には非同期入力ツール等の回答を待てる方法を使う。ツールがない場合は通常の質問で回答を待つ。各問に選択肢、推奨案、その案による振る舞いの違いを簡潔に示し、自由回答も受け付ける。
- 回答をspec.mdに逐次反映し、決定済み件数と残件数を示す。回答から追加の決定が必要になったら、理由、追加件数、更新した総数と残数を**追加質問の前に**提示する。
- 重要な未回答事項を時間経過で承認扱いにしない。待機中は依存しない調査を進める。開発者が明示的に判断を委任した事項は、採用案と理由を記録して進める。
- 全事項の決定後、仕様の要点を共有する。決定済みの内容に対して形式的な再承認を求めず設計へ進む。

仕様書には、目的、対象／対象外、画面と利用者ロール、正常・異常・境界の振る舞い、入力検証、保存・再表示、決定事項と回答、受入条件を含める。受入条件は `AC-01` のように識別し、前提・操作・期待結果を具体的に書く。「使いやすい」だけの検証不能な条件にしない。

## 3. 一時設計書から実装へ

- 確定したspec.mdを基に、**コーディング前に**同じ一時ディレクトリへdesign.mdを作る。
- ACごとに対象画面、コンポーネント、状態と遷移、データフロー、API・DB・Storage・権限制御、変更ファイル、互換性、検証方法を対応付ける。DB変更が必要なら既存の適用済みmigrationを改変せず新しいmigrationを検討する。
- 現在の構成はReact / TypeScript / Vite / React RouterとSupabase。入口は `src/components/Routes.tsx`、画面は `src/pages/`、共通UIは `src/components/`、認証は `src/contexts/`、処理は `src/lib/`、DBとAPIは `supabase/migrations/` と `supabase/functions/`。実行時に現状を確認する。
- 設計に沿って実装する。ユーザー／管理者の分離は画面だけでなく既存RLSやサーバー側検証と整合させる。新たな仕様判断が発生したら決定事項の件数を更新して対話へ戻り、仕様→設計→実装の順で同期する。
- スキル実行はローカルでの開発・検証を対象とする。デプロイ、push、本番データ変更は別途その操作への指示がある場合だけ行う。ローカルテストでも既存データを消すdb resetを安易に実行しない。

## 4. AIによる手動テストと修正の反復

- README、package.json、compose.yamlを確認してローカル環境を起動する。現在の起動候補は `npm run docker:dev`、既存ローカルバックエンドを使う場合は `npm run dev`。接続先がローカル／専用テスト環境であることを確認する。READMEと `supabase/seed.sql` のローカル用アカウントを使い、秘密情報を文書へ転記しない。
- ブラウザー操作ツールでAI自身が画面を開き、クリック・入力・送信・再表示・遷移を実施して結果を観察する。利用可能なbrowserスキルがある場合は読み、その操作手順に従う。自動テスト、ソース読解、HTTP疎通だけを手動テスト済みと扱わない。
- 各ACについて前提、使用ロール、操作手順、期待結果、観測した実結果、合否、証跡の場所をverification.mdへ記録する。画面確認はスクリーンショットや観測結果で裏付け、保存処理は再読み込み後も確認する。
- 対象に応じて正常系・必須入力・境界値・エラー・権限差・空データ・処理中表示・PC／スマートフォン幅を確認する。変更画面を重点的に検証し、全画面の表示、認証と主要遷移、および共通処理の影響先も回帰確認する。
- 現在の品質チェックは `npm run lint`、`npm run test`、`npm run build`（Docker経由の同等コマンドもある）。変更に関係する既存テストと必要な検証を実行する。DB/API変更では現行CIの該当検査も確認する。
- **不一致を見つけたら、原因を調べて実装を修正し、該当ACと影響範囲を再度手動テストする。全ACの合格を実際に確認できるまで反復する。** 実装を通すために受入条件を緩めない。要件変更が必要なら開発者との決定と仕様改訂を先に行う。
- ブラウザー・Docker・認証等の不足で検証できない場合は、解決可能な準備を行う。それでも実行不能なら、未検証のAC・具体的な障害・再開に必要な情報を伝え、検証保留として保存する。合格や完了を宣言せず、同じ障害への無意味な再試行も続けない。既存の検査失敗も区別して報告し、黙って無視しない。

## 5. 全画面の正本設計書

- 受入条件と回帰確認および必要な品質チェックの合格後、**今回変更した画面だけでなく、アプリケーション全体の現行設計**をdocsへ作成・更新する。ルーティングと画面実装を再調査し、新規画面、モーダル、旧URLのリダイレクトも漏らさない。
- 既存の正本があればその配置へ統合し、重複した正本を作らない。未整備なら `docs/design-index.md` を索引、`docs/architecture.md` を共通設計、`docs/screens/<画面名>.md` を各画面の正本とする。
- 現時点の画面候補は login (`/login`)、entry (`/entry`)、admin-users (`/admin/users`)、admin-responses (`/admin/responses`)、admin-settings (`/admin/settings`)。`/admin/rules` の転送と未定義URLの扱いも記載する。この一覧を固定せず実装から更新する。
- 各画面の設計書には目的、ルート、利用可能ロール、UI項目と制約、操作・状態遷移、正常／異常時、保存と取得、呼び出すAPI・関連テーブル、アクセス制御、関連コンポーネントと実装パス、確認済みの主要シナリオを記載する。モーダルやタブは所属画面内にまとめ、必要に応じて分割リンクする。
- 共通設計には全体構成、認証・権限、共有データ・API、画像保存、共通UI、画面間遷移をまとめ、各画面から参照する。画面別文書だけでは表現できないバックエンドもここで網羅する。
- 正本は実装済みの現状を記載し、将来案や未検証事項を実装済みとして書かない。最終状態のソースと照合し、全ルートの文書への対応、内部リンク、古い説明との矛盾を確認する。機密情報と一時ディレクトリにしか存在しない必須リンクを残さない。必要な検証結果は正本内に要約して残す。
- 完了時に、実装結果、手動確認と品質チェックの結果、正本設計書へのリンク、一時仕様書・設計書・検証記録の場所を簡潔に報告する。一時ファイルは検証や引き継ぎが終わる前に削除せず、正本とは区別する。
