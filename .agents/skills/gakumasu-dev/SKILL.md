# 学マスイベントアプリ開発

`$gakumasu-dev 回答一覧に応募部門の絞り込みを追加したい` のように、コマンドと短い要望で開始する。日本語で対話し文書を作る。開発は「仕様決定 → 文書・モック更新 → 開発者レビューと修正 → モック承認 → 実装 → 検証 → 正本設計書更新」の順に進め、開発者が最新のモックを明示的に承認するまで実装を開始しない。このスキル自体の作成・編集依頼では、アプリの開発フローを開始しない。

## 正本設計書の入口

- 最初に [docs/design-index.md](../../../docs/design-index.md) を読み、[共通設計](../../../docs/architecture.md) と索引で対応付けた `docs/screens/` の対象画面を参照する。
- DB・権限変更は [data-model.md](../../../docs/data-model.md) と [api.md](../../../docs/api.md)、画像変更は [images.md](../../../docs/images.md)、起動・CI変更は [operations.md](../../../docs/operations.md) も読む。
- 更新先はこの既存構成へ統合する。画面追加・削除は索引も更新し、設計書の相互リンクと実装根拠を維持する。[照合記録](../../../docs/verification.md) は確認時点と方法の記録であり、将来の変更の検証済み証拠として流用しない。
- 現状の文書化・設計書の整備だけを依頼された場合は、実装を正本として必要な調査と文書更新を行う。新機能開発向けの一時仕様書・設計・コーディング・手動テストの全フローは開始せず、指定された照合回数と確認方法を記録する。

## 2. 決定事項を細分化して対話する

### 洗い出しと粒度

- 最初の質問前に、今回変更する利用者の操作を開始から完了・再訪までたどり、下表の観点で未決事項を洗い出す。大枠の方針が決まっていても、利用者に見える細部まで確定したと扱わない。
- **1件は、他の回答を変えずに単独で選び直せる1つの判断とする。** 「表示仕様」「検索の動作」「エラー対応」のような議題名だけで数えず、具体的な質問に分ける。表示位置と初期値、選択方式と反映タイミング、再読み込み時と再ログイン時の保持はそれぞれ別件。複数の判断をセットにした選択肢で一括決定させない。
- 細かさは質問数のノルマで決めない。今回の変更に関係する観点を調べ、コード・正本設計書・今回の明示指示で確定する内容は根拠付きで記録する。類似画面の慣例やAIの推奨だけでは新機能の仕様を決定済みにしない。既存動作の維持を明示された範囲は再質問しない。
- 内部の関数名やライブラリ選定など、利用者の体験・業務ルールに影響しない実装判断はAIが行う。依頼範囲外の新機能を質問によって追加しない。

| 観点 | 独立した判断として確認する細部の例（該当するものだけ） |
| --- | --- |
| 対象・権限 | 対象画面、操作できるロール、閲覧できるデータ範囲、権限がない場合の非表示／無効表示 |
| 表示・導線 | 配置、ラベル、補助文、表示順、初期表示、スマートフォンでの配置や折りたたみ |
| 入力・選択 | 必須／任意、初期値、単一／複数選択、選択肢の範囲・順序、上限、空白・重複・境界値の扱い |
| 操作・組合せ | 即時反映／適用ボタン、条件同士のAND／OR、既存検索との組合せ、解除操作、並び順やページ位置の変化 |
| 保存・再訪 | 保存タイミング、画面移動・再読み込み・再ログインの各保持範囲、URL共有、キャンセルや未保存離脱時の扱い |
| 状態・失敗 | 初期データなしと検索結果0件の表示、処理中の表示・操作可否、失敗時の入力保持、エラー文言、再試行方法 |
| データ・業務境界 | 既存データへの適用、対象削除・変更時の扱い、期限ちょうどの判定、集計・件数・出力への反映範囲 |

### 質問と進捗管理

- **最初の質問を出す前に**「現時点で仕様確定に必要な未決定事項は N 件です」と件数および番号付き一覧を提示する。各項目に `D-01` のような固定IDと、何を選ぶかが分かる具体的な短文を付ける。大分類ではなく細分化した判断を数える。回答によって追加され得る条件付きの論点はその旨を示す。0件なら根拠を簡潔に伝えて進む。
- `spec.md` に `ID / 決めること / 状態 / 回答・採用内容 / 根拠・理由 / 依存ID / 対応AC` の決定台帳を持つ。状態は未回答・回答済み・既存根拠で確定・明示委任・対象外を区別する。推奨案は回答として記録しない。
- 利用可能なら対話型入力ツールで**1〜3件ずつ、各問1判断**を質問する。質問数を減らすために判断をまとめない。必須の仕様回答には非同期入力ツール等の回答を待てる方法を使う。ツールがない場合は通常の質問で回答を待つ。
- 各問は、対象画面・操作場面、決める点、具体的な選択肢、推奨案と短い理由、選択による動作の違いを示し、自由回答も受け付ける。「詳細はどうしますか」「一般的な仕様でよいですか」のような包括質問に逃げない。文言を決めるなら文言案、数値を決めるなら具体的な値を提示する。
- 依存関係のある判断は親を先に質問する。回答のたびに、選ばれた案によって必要になる細部・例外・境界を再点検し、次の1〜3件を選ぶ。親への回答だけで子の判断まで回答済みにしない。複数選択が選ばれた場合の選択上限・一致条件などは、それぞれ確定根拠を調べ、なければ追加質問にする。
- 回答をspec.mdに逐次反映し、質問対象の総数・決定済み件数・残件数を示す。追加が生じたら理由・追加件数・更新した総数と残数を**追加質問の前に**伝える。分岐で不要になった事項は対象外の理由を残し、残数から除外する。IDを振り直さず、曖昧な回答や一部だけの回答は該当箇所だけ具体的に聞き直す。
- 未回答を時間経過で承認扱いにしない。待機中は依存しない調査を進める。「任せる」は明示された範囲だけに適用し、採用案と理由を記録する。個別の推奨案への同意を、残り全部への委任に広げない。
- 設計へ進む前に、該当する観点の漏れと、正常・異常・境界・再訪の期待結果を書けるかを確認する。利用者に見える動作をAIが新たに仮定しないと書けない箇所は未決事項へ戻す。確定・明示委任・根拠付き対象外になったら仕様の要点を共有し、この時点では形式的な再承認を求めず、次の文書・モック更新へ進む。仕様への回答や同意は、後段のモック承認として扱わない。

### 粒度の例：応募部門の絞り込み

「絞り込みの仕様はどうしますか」の1件で済ませない。例えば未確定なら、以下を別々の判断として一覧化し、最初は1〜3件だけ質問する。既存根拠で確定できる項目は質問から除く。この例を固定の質問セットにはしない。

- D-01：部門は1つだけ選ぶか、複数選べるか。
- D-02：初期表示は全部門か、特定の部門か。
- D-03：選択変更で即時反映するか、適用ボタンで反映するか。
- D-04：条件変更時に現在のページを維持するか、先頭に戻すか。
- D-05：再読み込み後も選択した条件を保持するか。
- D-06：該当0件で表示するメッセージを何にするか。
- D-07：CSV出力の対象を絞り込み結果にするか、全件にするか（既存の出力機能に影響する場合）。

D-01が複数選択なら「いずれかの部門に一致／すべての部門に一致」は別の判断として確認する。D-05への回答から、画面再訪・再ログイン・別端末でも保持すると推測しない。

仕様書には、目的、対象／対象外、画面と利用者ロール、正常・異常・境界の振る舞い、入力検証、保存・再表示、決定台帳、受入条件を含める。受入条件は `AC-01` のように識別し、関連する決定ID、前提・操作・期待結果を具体的に書く。1つのACに複数の関連決定を対応付けてもよいが、細部の決定が受入条件から抜けないようにする。「使いやすい」だけの検証不能な条件にしない。

## 3. 一時設計書とモックを更新する

- 確定したspec.mdを基に、**アプリ実装前に**同じ一時ディレクトリへdesign.mdを作る。仕様変更のたびに両文書の該当箇所を更新し、モックと同じレビュー版（v1、v2など）を付ける。レビュー修正では既存文書を引き継ぎ、変更と影響先に関係する決定・AC・設計・確認結果を更新する。
- ACごとに対象画面、コンポーネント、状態と遷移、データフロー、API・DB・Storage・権限制御、実装予定の変更ファイル、互換性、検証方法を対応付ける。DB変更が必要なら既存の適用済みmigrationを改変せず新しいmigrationを検討する。画面で再現できる動作と、実装後に検証するバックエンドの条件を区別する。
- 既存の [mock/README.md](../../../mock/README.md) と [mock/DESIGN.md](../../../mock/DESIGN.md)、mock/source/の構成を読み、確定した仕様・設計に合わせて既存モックを更新する。別のモックを新設して既存モックを放置しない。対象画面の表示、操作、状態遷移、該当する正常・空・エラー・権限差を、サンプルデータとメモリー内の処理で確認できるようにする。保存・API・権限の動作は模擬し、実装済みの保証と混同させない。
- モックはバックエンド通信・永続化を行わない既存方式を維持する。認証やデータ処理の置換を保持し、本番ソースを一括コピーして実サービスへ接続させない。mock/source/の修正はまとめて行い、レビュー版を提示する前に現行のビルド手順（現在はリポジトリルートで npm run build:mock）でmock/app.js・mock/app.css等の配布成果物を再生成する。編集のたびにビルドを繰り返さず、配布物の確認後にソースを変更した場合は再生成・再確認する。開発者が開くmock/index.htmlに最新の変更が反映されていることを確認する。
- mock/README.mdには起動方法・確認シナリオ・模擬動作の制約を、mock/DESIGN.mdには今回のレビュー版・仕様との差分・未実装の予定・確認結果を反映する。バックエンド等をモックで確認できないACは、一時仕様書・設計書にも制約と実装後の検証方法を記す。docsの正本はこの段階で未実装の動作に書き換えない。
- 利用可能なbrowserスキルに従いAI自身もモックを開き、下記の確認範囲に沿って対象操作とPC／スマートフォン幅を確認する。verification.mdにレビュー版、変更箇所、影響先、確認した項目と結果を「モックの確認」として記録する。確認できない項目や起動障害は明示し、レビュー可能な状態を整える。モックの確認をアプリ実装の受入テスト済みとは扱わない。
- **承認前に変更できるのは、一時文書、モックのソース・サンプル・配布成果物、モックの説明文書などレビューに必要な範囲。** アプリのsrc/、supabase/、実装用テスト等の変更は承認後に行う。独立したモック作成をアプリ実装開始と取り違えず、実装を先行させてモックを生成することも避ける。

### モック確認の範囲

- **初回のモック提示では、今回の要望に必要な範囲を確認する。** 対象ACに対応する画面・操作・状態遷移と、関連する正常・空・エラー・権限差・境界、PC／スマートフォン表示を確認する。変更と関係しない画面の全件確認や、本実装向けの第6節の全画面回帰・品質チェックをモック提示の条件にしない。
- **レビュー修正では、変更箇所とその影響先に確認を絞る。** 直前のレビュー版との差分から、共通コンポーネント・CSS・状態・データ処理の利用先をたどって範囲を決める。例えば画像の水平位置だけの修正なら、対象画面と同じ計算を使うプレビュー、関連する画面幅・画像比率・表示境界を確認する。影響がない保存処理や別画面の操作まで一律に再確認しない。
- 確認済みで変更の影響を受けない項目は再実行せず、verification.mdに参照するレビュー版と影響がない根拠を簡潔に記す。「今回確認」「前版の記録参照」「未確認」を区別し、過去の結果を最新版で再実行した証拠として扱わない。以前から未確認の項目も未確認のまま明示する。
- 共通レイアウト・ルーティング・認証やメモリーアダプター・ビルド設定などの変更で影響が広がる場合、関連範囲を追加確認する。不具合や影響範囲の不明点が見つかった場合も、その根拠に応じて範囲を広げる。全画面へ影響する変更なら全画面を確認し、確認範囲を狭めるために必要な検証を省かない。
- 既存の検査があれば関連するものを使い、軽微な見た目の修正に大規模な代替テストや検査用基盤を新設しない。ブラウザーでしか確認できない描画・操作は実ブラウザーで確認する。利用できない場合は解決可能な準備を行い、それでも確認できなければ制約と未確認項目を記録して提示する。DOM検査等を追加して見た目を確認済みとは扱わない。

## 4. 開発者レビュー・修正・モック承認

- 文書とモックを揃えてから、開発者へspec.md・design.md・mock/index.html・mock/DESIGN.mdへのリンク、現在のレビュー版、起動方法、今回確認する画面・操作、主な変更点、模擬動作の制約を提示する。開発者が実際にモックを確認できるようにし、「この版のモックで問題なく、実装へ進めてよいか」を明確に確認して回答を待つ。承認を求める理由が、このスキルの「最新のモックの承認後に実装する」規定であることをスキルへのリンクとともに説明する。
- 修正要望があれば指摘と対応状況をspec.mdに記録する。新しい仕様判断が必要な点だけ第2節の対話へ戻り、決定台帳・ACを更新する。その後spec.md・design.md・モック・モックの説明文書の該当箇所を同じ内容に改訂し、レビュー版を上げ、配布成果物の再生成と第3節に沿った変更箇所・影響先の確認を行う。未変更の仕様・設計の再調査や確認済み検査の全件再実行を毎回の手順にしない。変更点と対応した指摘、今回の確認範囲・結果・未確認項目を添えて再提示する。**モックだけ、または文書だけを直してレビューを終えない。**
- 修正要望がなくなるまで「文書・モック更新 → 開発者の確認 → 指摘への対応」を繰り返す。仕様の合意、AI自身の確認成功、無回答や時間経過をモック承認とみなさない。「OK」など短い回答も、最新のモックに対する承認を尋ねた文脈で明確に承認を表す場合に限り採用する。条件付きの回答や未対応の指摘が残る場合は、対応して改訂版の承認を待つ。
- 最新版について明示的な承認を得たら、承認者（会話で特定できる範囲）、日時、承認の発言、承認対象のレビュー版と文書・モックのパスおよび変更ファイル、残っている模擬動作の制約をspec.mdへ記録し、段階を「承認済み」にする。その承認を実装開始の根拠として第5節へ進み、同じ実装開始の許可を重ねて求めない。
- 中断・再開時も承認記録と現在の版を照合する。承認済みの版から利用者に見える仕様・設計・モックが変わった場合は「レビュー待ち」に戻し、文書とモックを更新して変更後の版を再承認してもらう。実装で新たな仕様判断が生じた場合も、このレビュー手順へ戻る。承認済みの仕様へ合わせる不具合修正や、動作を変えない内部の実装判断には再承認を求めない。

## 5. 承認済みの仕様・設計・モックに沿って実装する

- 実装開始前に、未決事項・未対応のレビュー指摘がなく、現在の文書とモックの版に開発者の承認が記録されていることを確認する。承認記録がなければ第4節へ戻り、実装は待つ。
- 現在の構成はReact / TypeScript / Vite / React RouterとSupabase。入口はsrc/components/Routes.tsx、画面はsrc/pages/、共通UIはsrc/components/、認証はsrc/contexts/、処理はsrc/lib/、DBとAPIはsupabase/migrations/とsupabase/functions/。実行時に現状を確認する。
- 承認済みの仕様・設計・モックを基準にアプリを実装する。ユーザー／管理者の分離は画面だけでなく既存RLSやサーバー側検証と整合させ、模擬処理を実際のAPI・保存処理へ置き換える。モックの認証・メモリー内データ処理をそのまま本実装へ持ち込まない。利用者に見える動作を変える必要が生じたら、決定事項の件数を更新して対話へ戻り、文書・モックの更新と再承認を先に行う。
- スキル実行はローカルでの開発・検証を対象とする。デプロイ、push、本番データ変更は別途その操作への指示がある場合だけ行う。モックの提示や承認だけでは公開・デプロイへの指示にしない。ローカルテストでも既存データを消すdb resetを安易に実行しない。

## 6. AIによる手動テストと修正の反復

- README、package.json、compose.yamlを確認してローカル環境を起動する。現在の起動候補は `npm run docker:dev`、既存ローカルバックエンドを使う場合は `npm run dev`。接続先がローカル／専用テスト環境であることを確認する。READMEと `supabase/seed.sql` のローカル用アカウントを使い、秘密情報を文書へ転記しない。
- ブラウザー操作ツールでAI自身が画面を開き、クリック・入力・送信・再表示・遷移を実施して結果を観察する。利用可能なbrowserスキルがある場合は読み、その操作手順に従う。自動テスト、ソース読解、HTTP疎通だけを手動テスト済みと扱わない。
- 各ACについて前提、使用ロール、操作手順、期待結果、観測した実結果、合否、証跡の場所をverification.mdへ記録する。画面確認はスクリーンショットや観測結果で裏付け、保存処理は再読み込み後も確認する。
- 対象に応じて正常系・必須入力・境界値・エラー・権限差・空データ・処理中表示・PC／スマートフォン幅を確認する。変更画面を重点的に検証し、全画面の表示、認証と主要遷移、および共通処理の影響先も回帰確認する。
- 現在の品質チェックは `npm run lint`、`npm run test`、`npm run build`（Docker経由の同等コマンドもある）。変更に関係する既存テストと必要な検証を実行する。DB/API変更では現行CIの該当検査も確認する。
- **不一致を見つけたら、原因を調べて実装を修正し、該当ACと影響範囲を再度手動テストする。全ACの合格を実際に確認できるまで反復する。** 実装を通すために受入条件を緩めない。要件変更が必要なら開発者との決定、文書・モック改訂、第4節の再承認を先に行う。
- ブラウザー・Docker・認証等の不足で検証できない場合は、解決可能な準備を行う。それでも実行不能なら、未検証のAC・具体的な障害・再開に必要な情報を伝え、検証保留として保存する。合格や完了を宣言せず、同じ障害への無意味な再試行も続けない。既存の検査失敗も区別して報告し、黙って無視しない。

## 7. 全画面の正本設計書

- 受入条件と回帰確認および必要な品質チェックの合格後、**今回変更した画面だけでなく、アプリケーション全体の現行設計**をdocsへ作成・更新する。ルーティングと画面実装を再調査し、新規画面、モーダル、旧URLのリダイレクトも漏らさない。
- 既存の正本があればその配置へ統合し、重複した正本を作らない。未整備なら `docs/design-index.md` を索引、`docs/architecture.md` を共通設計、`docs/screens/<画面名>.md` を各画面の正本とする。
- 現時点の画面候補は login (`/login`)、entry (`/entry`)、admin-users (`/admin/users`)、admin-responses (`/admin/responses`)、admin-settings (`/admin/settings`)。`/admin/rules` の転送と未定義URLの扱いも記載する。この一覧を固定せず実装から更新する。
- 各画面の設計書には目的、ルート、利用可能ロール、UI項目と制約、操作・状態遷移、正常／異常時、保存と取得、呼び出すAPI・関連テーブル、アクセス制御、関連コンポーネントと実装パス、確認済みの主要シナリオを記載する。モーダルやタブは所属画面内にまとめ、必要に応じて分割リンクする。
- 共通設計には全体構成、認証・権限、共有データ・API、画像保存、共通UI、画面間遷移をまとめ、各画面から参照する。画面別文書だけでは表現できないバックエンドもここで網羅する。
- 正本は実装済みの現状を記載し、将来案や未検証事項を実装済みとして書かない。最終状態のソースと照合し、全ルートの文書への対応、内部リンク、古い説明との矛盾を確認する。機密情報と一時ディレクトリにしか存在しない必須リンクを残さない。必要な検証結果は正本内に要約して残す。
- 完了時に、実装結果、承認されたモックの版と確認場所、手動確認と品質チェックの結果、正本設計書へのリンク、一時仕様書・設計書・承認記録・検証記録の場所を簡潔に報告する。一時ファイルは検証や引き継ぎが終わる前に削除せず、正本とは区別する。
