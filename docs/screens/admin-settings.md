# 設定画面

[索引](../design-index.md) / [画像](../images.md) / [DB](../data-model.md) / [API](../api.md)

## 目的・ルート

`/admin/settings`、admin専用。旧 `/admin/rules` はここへ転送。開催回の作成・編集と回答受付対象切替を行います。event_editionsを作成日時降順で取得し、指定回、active回、先頭、新規開催の順で選択します。

共通Headerにライト／ダークテーマの切替を表示します。端末連動と保存規則は[共通設計](../architecture.md)を参照します。

## 項目と検証

| 項目 | 内容 |
| --- | --- |
| 編集する開催回 | 既存回＋新規開催。新規は名称・ルール・日時・2キャラクターを空へ初期化 |
| 名称 | trim後必須、入力maxLength=100 |
| ランキング公開 | 開催回欄のチェック。既存回・新規回とも初期非公開。「設定を保存」で他設定と保存。受付期間・受付対象切替とは独立 |
| 応募期間 | datetime-local、双方任意。両方ある場合start < end。ブラウザー時刻で表示、ISOへ変換して保存 |
| ページ画像 | login/entryの2枚。片方だけ指定はエラー。新規作成時も未指定なら開催回自体は保存可能 |
| キャラクター | 13名から重複しない2名。入れ替えボタンあり |
| 応募部門 | 対象キャラクター直後。1〜10部門の追加・削除、名称/補足/参加条件文と証明必須を編集。下記参照 |
| ルール説明 | 専用モーダル、最大10,000文字 |

既存回のcharacter_optionsが2要素でない場合、画面は既定の星南・燕を使います。開催回選択が変わると画像選択をリセットします。各欄を編集しただけではDBへ保存しません。

## 設定保存

session、ルール長、名称、2キャラクター、期間、画像ペアを検証後、名称・ルール・日時・character_options・division_settings・ranking_published・updated_byをevent_editionsへINSERTまたはUPDATEします。新規時は返却idを使用します。

「ランキングを公開する」の変更だけでは保存しません。回切替で保存済みの値を読み直し、未保存変更を破棄します。保存失敗時はチェックを保持してエラー表示。設定を保存した後は再訪・再読込・再ログインでもDBの公開設定を読み込みます。管理者のみ更新でき、一般ユーザーの直接UPDATEも既存RLSが拒否します。ランキング側への反映は次回のデータ取得時です。

画像ペアがあればZIPをStorageへupsertし、page_images_pathを更新。成功後は一覧を再取得して保存した回を選択し、作成／保存メッセージを表示します。DB成功後の画像失敗は「開催回の設定は保存しましたが…」と部分成功を通知し、開催回を消去しません。

## ルールモーダル

開いた時点のルールをdraftへコピー。「過去の開催回から呼び出す」は現在編集中のIDを除く全開催回を候補にして選択内容をdraftへコピーします。作成日時による過去判定はありません。

既存回はモーダル内保存でrules_descriptionとupdated_byを即時更新し、一覧再取得。新規回はローカルrulesへ保持し、外側の設定保存でDBへ反映します。保存中はボタン無効でonCloseも無視します。既存回の保存後は再取得でフォーム全体を設定し直すため、外側で未保存の名称・日時等を保持する保証はありません。

## 画像調整モーダル

選択時に圧縮し、canvas上で拡大率・位置を調整して確定します。保存済み画像はStorage ZIPからプレビュー。開催回変更直後に旧画像を隠し、取得・デコード完了までは両欄にスピナーだけ表示します。失敗時はスケルトンと既存の保存済み画像取得エラー通知を表示し、公開画像を一時的に代用しません。詳細な比率・圧縮・キャッシュは画像設計を参照。

## 受付対象切替

新規回または既にactiveな回では切替ボタンdisabled。保存済みpage_images_pathが必須で、画面内の未保存画像では代替しません。DEVはStorage画像を先に取得し、set_active_event RPCが成功した後、開催回IDと画像ペアをローカルキャッシュへ反映します。本番ビルドはactivate-event Functionを呼びます。

成功後に開催回を再取得して成功通知。画像取得失敗、API失敗は固定日本語文言。切替API失敗時は別開催回のキャッシュへ更新しません。切替中は開催回選択と受付対象切替ボタンを無効化し、二重操作を防ぎます。確認モーダルはありません。

設定保存だけではactiveは変えません。本番の画像公開はWorkflow完了後です。active回の画像保存だけでは再デプロイは始まりません。

## 照合シナリオ（ソース確認）

- 新規と既存の初期値・保存先・ルール保存時点の差。
- 重複キャラクター、逆転した期間、片方だけの画像を拒否。
- 設定DB更新と画像保存の部分成功。
- 保存と受付対象切替、DEVと本番の経路を分離。

## 応募部門の編集（2026-11-24）

「部門を追加」は10部門で無効、削除は1部門で無効。名称は必須50文字、補足は任意200文字、参加条件は全部門で任意500文字。前後trim・文中改行保持、同じ開催回の名称重複不可。空文は回答画面で非表示。部門IDは追加時UUIDで固定、表示順は既存順と追加順をorderへ保存します。

新規部門は空欄と証明必須オフ。証明必須をオンにするとPID・Pレベルと総出席日数の2画像を要求します。最新回があれば新規開催に全設定と部門数を独立コピーし、0回なら1部門の空欄で開始。編集のみでは保存せず「設定を保存」で他設定と一緒に保存。回切替/離脱は未保存変更を破棄。保存失敗は入力保持、処理中はフォーム操作と二重保存を無効にします。

管理者限定get_event_division_usageで回答件数を取得し、回答がある部門は削除・証明要件変更を無効にして理由を表示。名称と案内は編集可能です。件数取得中/失敗中も削除と証明変更は無効。古い回の応答は破棄します。削除できる場合は対象名と「設定を保存」で確定する旨をモーダル表示し、キャンセル/削除を選択。DBも保存時に回答済み部門を保護します。

保存後の名称は次回取得時に回答入力・本人履歴・管理/一般ランキング・管理表・CSVへ反映。保存済み回答も対象です。[DivisionSettingsEditor](../../src/components/settings/DivisionSettingsEditor.tsx)、[部門処理](../../src/lib/divisions.ts)、[設定統合テスト](../../src/pages/SettingsDivisions.test.tsx)、[DB制御](../data-model.md)。実ブラウザーでのPC/スマホ・テーマ別描画と削除モーダル操作は保留。[検証記録](../verification.md)。
